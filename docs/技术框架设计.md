## 1. 技术选型

### 1.1 结论

| 项 | 选择 | 理由摘要 |
| --- | --- | --- |
| 语言 / 框架 | **C# + WPF** | 系统集成最顺（窗口行为、拖放、剪贴板、托盘均为原生能力）；常驻资源占用小；打包体积小；生态成熟 |
| 目标框架 | `net8.0-windows` | LTS；需要先安装 .NET SDK（本机当前只有 7.0.20 运行时，无 SDK） |
| 界面描述 | XAML + Fluent 风格控件库 | 无需引入 Vue/React 等 Web 前端 |
| 数据存储 | 本地 JSON（`System.Text.Json`） | 条目量小，无需数据库 |
| 网络 | **无** | 纯本地工具 |

### 1.2 备选与排除

| 方案 | 判断 | 关键理由 |
| --- | --- | --- |
| Python + PySide6/Qt6 | 唯一合理备选 | 拖放能力完备，开发快、代码易读易改；代价是打包 60～150 MB、冷启动 1～3 秒、常驻 80～150 MB、PyInstaller 杀软误报 |
| Java 21 + JavaFX | 不推荐 | `Dragboard` 三种格式都支持，但"不抢焦点窗口"无 API、JVM 常驻 150～300 MB、分发 150 MB+、桌面生态边缘化 |
| Electron / Tauri | 排除 | 官方出站拖拽只支持文件路径，文字与图片拖不出去；为小面板常驻 Chromium 不划算 |
| AutoHotkey | 排除 | 无法实现文字/图片出站拖拽 |

## 2. 总体架构

```
┌─────────────────────── 中转站（单进程 WPF 应用） ───────────────────────┐
│                                                                        │
│  App 层（UI / 生命周期）                                                │
│    App.xaml         单实例守护、托盘、全局快捷键、开机自启               │
│    ShelfWindow      浮窗三态、贴边隐藏、不抢焦点                         │
│    SettingsWindow   设置页                                              │
│    ViewModels       MVVM 绑定与命令                                     │
│                              │                                          │
│  Core 层（领域逻辑，无 UI 依赖，可单测）                                 │
│    Item / Shelf           条目模型与暂存区状态                           │
│    ItemStore              持久化、上限与过期淘汰                         │
│    NameRepair             文件名乱码修复（编码双向试探 + 打分）          │
│    PathListFormatter      路径清单生成                                   │
│    CleanupService         过期清理、退出清理、崩溃恢复                   │
│                              │                                          │
│  Platform 层（Win32 互操作与平台服务）                                   │
│    WindowService     置顶、不抢焦点、贴边、DPI、显示器工作区             │
│    ClipboardBroker   读写剪贴板、格式协商、自产标记、占用重试            │
│    DragOutService    出站拖放（三格式同挂）                              │
│    DragInHandler     入站拖放（文件/文字/图片）                          │
│    ShellService      打开文件、在资源管理器中定位                        │
│    SourceWatcher     目录监听 + 文件稳定判定                             │
│    ThumbnailProvider 缩略图与懒加载                                      │
│                                                                        │
└────────────────────────────────────────────────────────────────────────┘
      │                        │                          │
 %LOCALAPPDATA%           源文件（只读引用）          外部应用
 状态 + 图片缓存       （永不复制、永不删除）    （微信 / Codex / 资源管理器）
```

**进程模型**：单进程、单实例（第二次启动直接唤出已有窗口）。无后台服务、无网络连接。

## 3. 模块职责

| 模块 | 职责 | 不做什么 |
| --- | --- | --- |
| `WindowService` | 窗样式、置顶、贴边、DPI、显示器工作区计算 | 不处理业务逻辑 |
| `ClipboardBroker` | 读写剪贴板、格式协商、重试、自产标记 | 不长期持有内容（除无源图片落盘） |
| `DragOutService` | 组装多格式 `DataObject` 并启动拖放 | 不负责删除源文件 |
| `DragInHandler` | 解析拖入数据为 `Item` | 不直接写持久化 |
| `ItemStore` | 内存集合 + JSON 持久化 + 上限与过期 | 不碰剪贴板与窗口 |
| `SourceWatcher` | 监听白名单目录、稳定判定、去重 | 不递归全盘 |
| `NameRepair` | 乱码修复建议与打分 | 不自动改写文件（必须用户确认） |
| `CleanupService` | 过期清理、退出清理、孤儿缓存回收 | 不删除用户文件 |

## 4. 数据模型

### 4.1 条目模型

```jsonc
{
  "schemaVersion": 1,
  "items": [
    {
      "id": "b6f1c0e2...",              // GUID
      "kind": "file",                    // file | folder | text
      "displayName": "示例文档.pptx",      // 可被用户重命名
      "path": "C:\\Users\\<user>\\xwechat_files\\...\\2026-09\\示例文档.pptx",
      "text": null,                      // 仅文字条目
      "cachePath": null,                 // 仅无源图片：缓存 PNG 的绝对路径
      "createdAt": "2026-09-27T21:14:50+08:00",
      "pinned": false
    }
  ]
}
```

说明：`state`（是否失效）与来源信息**不落盘**——前者在启动时按路径是否存在重新计算，后者属于后续版本。
属性名写 camelCase、枚举值写小写（`file` / `folder` / `text`），读取时大小写不敏感。

### 4.2 持久化

| 项 | 设计 |
| --- | --- |
| 位置 | `%LOCALAPPDATA%\TransitShelf\state.json` |
| 缓存 | `%LOCALAPPDATA%\TransitShelf\cache\`（仅无源图片的 PNG） |
| 写入方式 | 原子写：先写 `state.json.tmp`，再替换正式文件 |
| 版本字段 | `schemaVersion`，便于后续迁移 |
| 启动时校验 | 逐条检查路径是否存在，缺失则标记 `missing`；清理过期缓存 |

### 4.3 关键约束

1. **零拷贝**：文件与文件夹条目只存路径，不复制内容。
2. **无源图片必须落盘**：剪贴板位图一旦被覆盖就丢失，必须存为缓存 PNG 才能可靠投递。
3. **删除条目 ≠ 删除文件**：任何清理路径都必须与用户文件系统操作严格隔离。

### 4.4 排序不变式与清空语义

| 规则 | 说明 |
| --- | --- |
| 钉住置顶 | 顺序恒为"钉住的在前（各自按收录时间倒序）、未钉住的后"。新增、切换钉住、启动恢复后都重新应用 |
| 清空只清未钉住 | `ClearUnpinned()` 保留钉住项，并回报"清掉几项、保留几项"；要清掉钉住的必须先取消钉住 |
| 淘汰只看未钉住 | 超出上限时淘汰最旧的未钉住项，钉住项永不参与淘汰与过期 |

> 为什么必须重排：新条目默认插在列表最前，若不重排，"钉住"就只是"不会被清理"，
> 而用户对钉住的直觉是"固定在顶部别动"，两者不一致就会被当成 bug。

### 4.5 工作区与分组（2026-10-18 续接 10-10 已确认方案 B）

- 关联 FR-01 / FR-41 / FR-60 / FR-61 / FR-75；ADR D28。沿用 C# / WPF 与现有主题，不新增依赖。
- `ShelfGroup` 保存 Id / Name / CreatedAt，`WorkspaceService` 管理分组；条目的 `GroupId = null` 表示临时区，其余表示工作区分组。状态格式升级到 v3，保存 groups 与 groupId；v1/v2 缺省字段按临时区读取。
- 上限、TTL、退出清空只作用于临时区。关闭工作区只隐藏入口，分组和条目仍保存；再次开启可恢复。加载时缺失分组的条目移回临时区并钉住，防止状态损坏导致静默丢失。
- 开关开启后出现「临时区 / 工作区」按钮。工作区 320 × 520，分组选择用菜单（长名截断、完整名提示）；同一行提供新建与管理。没有分组时显示创建引导；空组显示拖入引导。重命名使用可输入的独立对话框，Enter 保存、Esc 取消，只有此类显式输入才允许激活。
- 列表过滤到当前区域；手动添加、收录、拖入放在当前分组，目录自动收录始终进临时区。尚无分组时手动收录提示先建组。切换区域或分组清掉多选与清空确认状态，防止操作跨区串联。
- 条目右键提供「钉入工作区 / 移动到分组」与「移回临时区」。移回临时区保留钉住状态，提醒会恢复上限和过期约束；确需淘汰时回报数量。整组复制复用 PathListFormatter，跳过文字并说明。
- 删除分组先确认，组内条目移回临时区并钉住，不删除条目或源文件。面板清空仅针对当前区/组且保留钉住项；托盘清空始终只清临时区。
- 分组与条目共同延迟落盘、退出前同步保存，启动先恢复分组再清理条目。回归覆盖分组管理、跨区去重、容量/TTL 隔离、清空作用域、旧格式兼容与分组持久化。真实系统焦点、DPI 与跨应用粘贴仍需手工验收。

### 4.6 搜索与类型过滤（FR-44）

- 过滤只作用于当前正在查看的区域：临时区或当前工作区分组；不会改变持久化条目、排序或清理规则。
- 搜索词按不区分大小写的包含关系匹配显示名、源路径和文字内容；空搜索词表示不过滤。匹配在内存中完成，不做全盘索引或网络请求。
- 类型筛选提供「全部类型 / 文件 / 文件夹 / 图片 / 文字」。无源图片在领域模型中仍是 `ItemKind.File`，通过 `ShelfItem.IsImage` 单独归类；「文件」筛选排除图片，避免图片同时出现在两个类别。
- Core 提供纯函数 `ShelfItemFilter.Matches` 与 `ShelfFilterKind`，由单元测试覆盖组合条件；WPF 使用现有 `ICollectionView.Filter`，输入变化后立即调用 `Refresh()`。
- 过滤后没有匹配项时保留当前区域的条目，不显示“空区域”引导，改为提示调整搜索词或类型；底部计数显示当前区域的可见数与总数。

## 5. 关键流程

### 5.1 拖入

```
用户拖拽 → DragEnter（整框高亮）
        → DragOver（判定是否含可用格式）
        → Drop：按优先级解析
             ① FileDrop → 每个路径生成 file / folder 条目
             ② UnicodeText → 生成 text 条目
             ③ Bitmap / PNG → 有源文件存路径，无源文件写缓存 PNG
        → ItemStore.Add（同路径同类型去重）
        → 刷新 UI 并持久化
```

### 5.2 复制与粘贴（主通道）

```
单击条目 → ClipboardBroker.Set(...)
             文件：DataObject 挂 CF_HDROP（路径列表）
             文字：UnicodeText（浏览器来源可附带 HTML）
             图片：Bitmap/DIB + PNG 两份
        → 打"自产标记"（自定义格式），防止自己的监听再次收录
        → 用户切到目标应用 → Ctrl+V
```

### 5.3 拖出（可选增强）

```
按住条目移动超过阈值 → 组装 DataObject：
      文件 / 文件夹 → SetData(DataFormats.FileDrop, string[])
      文字         → SetData(DataFormats.UnicodeText, text)
      图片文件      → 上面两种之外，再附 SetData(DataFormats.Bitmap, BitmapSource)
                      与 SetData("PNG", stream)，由目标应用自取
  → DragDrop.DoDragDrop(...) 启动 OLE 拖放
  → 目标应用自取它能识别的格式
```

> **按类型挂载，而不是无差别挂三种格式**。若给文件条目同时挂上纯文本，
> 目标应用可能优先取到文本，把"发文件"变成"往输入框里插一条路径"。只有图片是有意同时提供三种形式。

### 5.4 目录监听（P1）

```
FileSystemWatcher（白名单目录，含微信按月分桶目录）
  → 事件去抖（同一文件 700 ms 内只处理最后一次，期间再有事件则重新计时）
  → 稳定判定：连续两次采样都能"非空 + 可独占打开"（间隔 400 ms），最多等 15 轮
  → 过滤：.tmp/.temp/.part/.crdownload 等临时后缀、以 . 或 ~ 开头的文件、本工具缓存目录
  → 回调切回 UI 线程后再入架（FileSystemWatcher 回调在后台线程）
```

监听目标由 `WatchTargets.Resolve` 计算（纯函数、有单元测试）：

| 开关 | 目标目录 |
| --- | --- |
| 自动收录下载目录 | `%USERPROFILE%\Downloads` |
| 自动收录微信接收目录 | `%USERPROFILE%\xwechat_files\<wxid>\msg\file`（微信 4.x）与 `%USERPROFILE%\Documents\WeChat Files\<wxid>\FileStorage\File`（3.x 遗留） |
| 额外目录 | `settings.extraWatchDirectories`（供用户自定义，也是验收脚本使用的注入点） |

两个开关**默认关闭**（红线 R6），状态存在 state.json 的 settings 里，托盘菜单勾选即可切换。

### 5.5 过期与清理

```
运行中（变更 500 ms 后）→ 原子写入 state.json
退出时 → 保存全部条目（不删任何东西，保护现场）
启动时 → 逐个校验源文件是否存在（失效则标记，不删除）
        → 未钉住且超过 TTL（默认 24 小时）的条目丢弃
        → 扫描缓存目录，删除不被任何条目引用的孤儿文件
```

> 为什么退出时不清理：关掉工具或重启电脑之后，临时区里的东西仍应还在；真正的清理交给 TTL 与手动清空，
> "退出即清空"留作后续设置项。

## 6. 关键技术实现要点

### 6.1 不抢焦点的置顶浮窗

| 要点 | 做法 |
| --- | --- |
| 不抢焦点 | 窗样式加 `WS_EX_NOACTIVATE`；`ShowActivated="False"`；处理 `WM_MOUSEACTIVATE` 返回 `MA_NOACTIVATE` |
| 不进 Alt+Tab / 不显示在任务栏 | 样式加 `WS_EX_TOOLWINDOW`；`ShowInTaskbar="False"` |
| 置顶 | `Topmost = true`（等价 `WS_EX_TOPMOST`），必要时 `SetWindowPos(HWND_TOPMOST)` 重新压顶 |
| 圆角与材质 | Windows 11 用 `DwmSetWindowAttribute`（圆角偏好、系统背景材质）。**慎用 `AllowsTransparency=True`**：它会切换窗口渲染路径，历史上存在性能与文字模糊问题，优先走 DWM 方案 |
| 兜底模式 | 若与个别软件（输入法、录屏、游戏）冲突，提供"仅快捷键唤出"模式 |

### 6.1.1 展开与收起的触发链路

| 触发方式 | 实现要点 | 默认 |
| --- | --- | --- |
| 点击把手 / 托盘 / 全局快捷键 | 直接切换窗口状态 | 开启 |
| **拖拽经过热区自动展开** | 收起态保留 4～6 px 可见热区，并将其注册为拖放目标；系统拖拽光标进入时触发 `DragEnter` → 立即展开面板。**不要用鼠标钩子做"是否正在拖拽"的启发式判断**：Windows 没有公开 API，结果不可靠 | 开启 |
| 静止悬浮展开 | 光标停留在热区 300 ms 后展开（移出 400 ms 后收起），降低误触发 | 开启（可关） |
| 收起：鼠标移出 | 移出面板区域 400 ms 后收起（仅悬浮展开场景） | 开启 |
| 收起：Esc / 再按快捷键 / 收起按钮 | 立即收起 | 开启 |
| **失焦不收起** | 面板本身不抢焦点，若失焦即收起，用户切窗口时面板会莫名消失 | 强制 |

> 热区必须保留可见像素：面板若完全隐藏到 0 px，系统拖拽无法命中，`DragEnter` 不会触发。

### 6.1.2 与其他置顶窗口的竞争（不抢焦点带来的副作用）

`WS_EX_NOACTIVATE` 让浮窗永不激活，代价是：**Windows 在置顶层内部按激活先后排序**，
因此任何别的置顶窗口（被"置顶"的微信窗口、其他常驻置顶小工具）都会永久盖住我们，
而我们既不在任务栏、又没有托盘入口，用户就"找不到"了。这是必须处理的结构性问题。

| 措施 | 说明 |
| --- | --- |
| 抢位心跳 | 每 4 秒调用一次 `SetWindowPos(HWND_TOPMOST, SWP_NOMOVE｜SWP_NOSIZE｜SWP_NOACTIVATE)`，在不激活、不移动的前提下把窗口送回置顶层顶部；展开/收起时也立即调用一次 |
| 样式补写 | WPF 在样式变化时可能重写扩展样式，每次抢位顺带补回 `WS_EX_NOACTIVATE` 与 `WS_EX_TOOLWINDOW` |
| 托盘图标 | 不进任务栏与 Alt+Tab 的窗口必须有托盘入口，菜单提供"显示/收起/清空/退出"，双击唤出（见 `App.CreateTrayIcon`） |
| 全局快捷键 | `Ctrl+Alt+D` 唤出/收起；注册失败（被别的软件占用）时不影响其他功能，仅在状态栏提示 |
| 收录快捷键 | `Ctrl+Alt+C` 收录剪贴板内容，并顺带唤出面板给出反馈 |

### 6.1.3 收录剪贴板的优先级与无源图片

`ClipboardService.Read()` 一次性取快照，优先级为**文件 &gt; 文字 &gt; 图片**（一次收录只处理一类，避免把同一份内容拆成多条）。

- 文件：走 `CF_HDROP`，逐个生成条目。
- 文字：生成文字条目。
- 图片：剪贴板位图**当场冻结并写成缓存 PNG**（`ImageCacheService`，落在 `%LOCALAPPDATA%\TransitShelf\cache\clip-时间戳-随机.png`），
  条目只保存该路径（红线 R8：绝不长期持有位图）。缓存文件由启动时的孤儿清理负责回收。

**实测证据（2026-09-27）**：另起一个置顶窗口覆盖胶囊位置后 1.2 秒，`WindowFromPoint` 返回该竞争窗口
（确认被压住）；等待 5 秒后再次查询，返回本程序窗口（确认抢回）。

### 6.2 贴边隐藏与多屏

- 位置计算基于当前显示器的**工作区**（排除任务栏），而不是屏幕总尺寸。
- 收起态只留 4～6 px 可见，鼠标进入占位区域即展开；展开方向根据浮窗所在侧自动镜像。
- 监听 `WM_DISPLAYCHANGE`、`WM_DPICHANGED` 与系统 `DisplaySettingsChanged` 事件，重新计算位置，避免拔插显示器或改缩放后窗口漂移。

### 6.3 入站拖放

- WPF 侧：`AllowDrop = true`，处理 `DragEnter` / `DragOver` / `DragLeave` / `Drop`。
- 格式判定顺序：`DataFormats.FileDrop` → `DataFormats.UnicodeText` → `DataFormats.Bitmap` → 自定义 `"PNG"`。
- 拖入时整框高亮 + 显示"松手即放入"，松手后立即出条目（目标 ≤ 300 ms）。

### 6.4 出站拖放

- 用 `System.Windows.DataObject` 一次挂多格式，再调 `DragDrop.DoDragDrop(element, dataObject, DragDropEffects.Copy)`。
- **不要**只挂文件格式：微信以外的目标（浏览器输入区、文档编辑器）可能只认文本或图片。
- 拖拽源元素需保持存活，拖放过程中不要销毁条目视图。

### 6.5 剪贴板

| 问题 | 处理 |
| --- | --- |
| 剪贴板被其他进程占用导致写入抛异常 | 重试循环（最多 4 次，每次间隔 30 ms；都在 UI 线程上，总时长必须短） |
| 写入被拒绝的**异常类型不止一种** | 捕获一切异常（不能只捕 `COMException` / `ExternalException`，见下方"静默失败"） |
| 主通道（WPF `Clipboard`，走 OLE）整体不可用时 | 后备通道：绕开 OLE，用 Win32 `OpenClipboard` + `SetClipboardData` 直写 `CF_HDROP` / `CF_UNICODETEXT`（`NativeMethods.TrySetClipboardFileDrop` / `TrySetClipboardText`） |
| 两条通道都失败 | 返回 false，界面提示"复制失败，请重试"，并把最后一次异常写进 `error.log`（`Diagnostics.LogFailure`） |
| 自己写入又被自己监听 | 写入时附带自定义格式作为"自产标记"，读取时命中即跳过 |
| 监听剪贴板变化 | 用 `AddClipboardFormatListener` + `WM_CLIPBOARDUPDATE`，比轮询省电 |
| 进程退出后内容仍可用 | 使用带持久化的写入方式，使路径列表在进程退出后仍可粘贴 |
| 位图体积大 | 不长期持有位图；无源图片立即落缓存 PNG，UI 只持有缩略图 |

> **重试耗尽后必须"返回失败"，不能"抛出异常"**：剪贴板可能被别的进程长时间占用
> （`CLIPBRD_E_CANT_OPEN`）。早期实现里最后一次重试的异常会逃逸出去，直接终止整个常驻进程——
> 用户看到的现象就是"用着用着窗口就消失了"。现在重试全失败时返回 false，界面提示"复制失败"。

> **静默失败（2026-10-06 实机修复）**：只捕 `COMException` / `ExternalException` 是不够的。
> 实机在 `error.log` 里抓到两次单击条目复制文件失败，异常是 `NotImplementedException`
> ——`OleSetClipboard` 返回 `E_NOTIMPL`(0x80004001)，被 `ThrowExceptionForHR` 映射成
> `NotImplementedException`，它既不是 `COMException` 也不是 `ExternalException`，从两个 catch
> 旁边溜走，一路逃到 `App.DispatcherUnhandledException` 被吞掉：**复制静默失败，界面连提示都没有**。
> 两条对策：① 写入路径捕获一切异常，按"重试→返回 false"处理；② 主通道失败后走 Win32 直写后备通道
> （不经过 OLE，数据由系统持有，程序退出后仍可粘贴）。回归用例见
> `src/TransitShelf.Tests/ClipboardServiceTests.cs`。

### 6.5.1 展开模式不能被悬浮劫持

展开有"悬浮展开（移开即收）"与"主动展开（常驻）"两种模式。鼠标经过一个已经主动展开的面板时，
**不得把模式改写成悬浮模式**，否则用户点开面板后再去别的软件，面板会被自动收起——这正是"找不到窗口"的成因之一。
实现上：悬浮只在收起状态触发；主动展开（点击胶囊 / 快捷键 / 拖拽经过）始终置为常驻。

### 6.5.2 常驻工具不得因单次异常退出

`App.DispatcherUnhandledException` 统一兜底：标记 `Handled = true` 让程序继续运行，
并把异常追加写入 `%LOCALAPPDATA%\TransitShelf\error.log` 供排查。
一个常驻置顶工具"静默消失"的代价远高于"某个功能暂时失灵"。

### 6.6 文件名乱码修复算法

```
输入：疑似乱码的文件名
1) 候选生成
   a. name → Latin1 字节 → UTF-8 解码      （修复 æ–‡ä»¶ 类）
   b. name → GBK   字节 → UTF-8 解码      （修复 鏂囦欢 类）
   c. name → UTF-8 字节 → GBK   解码      （反向错配）
2) 候选打分
   命中 CJK 统一汉字的比例 + 常见中文词命中 - 异常字符惩罚（锟 / 鏂 / æ / Ã）
3) 输出
   得分显著高于原名 → 展示"建议名 + 预览"，由用户一键应用
   含替换字符（U+FFFD）等不可逆损坏 → 明确提示"无法自动修复，请手动改名"
```

实现注意：.NET 中读取 GBK(936) 需先注册 `CodePagesEncodingProvider.Instance`，否则 `Encoding.GetEncoding(936)` 会抛异常。

**两个实测踩到的坑（实现里必须保留这两条防线）**：

1. **判据不能用"中文占比"**：乱码本身往往也是合法汉字（`鏂囦欢`），占比一样高。
   改用"能否**干净解码**"：真乱码按字节还原后能被 UTF-8 严格解码且无替换字符，正常中文名做同样操作会解出非法序列。
2. **不要直接用 `Encoding.Latin1`**：它的默认回退是替换字符，遇到汉字会悄悄变成 `?`，
   于是正常文件名会被"修复"成一串问号——而且全 ASCII，反而被判成干净解码。
   所有源编码必须使用 `EncoderFallback.ExceptionFallback`，并加兜底规则：**候选名不得比原名多出问号或替换字符**。
3. 不要加入"UTF-8 字节→按 GBK 解释"的反向候选：GBK 覆盖很宽，正常中文名的 UTF-8 字节也常能被 GBK 干净解码，误判率高。

### 6.9 单击语义：按类型区分主动作

| 类型 | 单击 | 双击 | 理由 |
| --- | --- | --- | --- |
| 文件夹 | **打开**（系统默认文件管理器进入该目录） | 打开 | 文件夹没有"复制内容"的自然语义，进入目录是它唯一的高频动作 |
| 文件 | 复制 | 打开（默认程序） | 风险不对称：误触发"打开"会启动程序并抢走焦点，误触发"复制"静默无害且可覆盖 |
| 文字 / 图片 | 复制 | 打开预览 | 内容类条目的自然动作是搬运，不是查看 |

每张卡片悬停时显示 `[打开] [复制] [定位]` 三个显式按钮，行为可见、不依赖用户猜测。以上默认值由设置项 `FR-70` 统一覆盖。

### 6.10 多选与批量操作条（FR-21）

```
点「多选」→ 进入多选模式：头部按钮整排换成批量操作条
         → 点条目 = 勾选 / 取消勾选（选中态：描边 + 浅色底）
         → 「复制所选内容」→ PathListFormatter 生成路径与文字的顺序文本，同时挂载 CF_HDROP + CF_UNICODETEXT
         → 「完成」退出多选模式（清空选中，恢复头部按钮）
```

几处刻意的取舍：

- **用显式「多选」按钮进入，不用 Ctrl+点击**。本窗口带 `WS_EX_NOACTIVATE` 永不激活，
  修饰键状态在无焦点窗口上不可靠；按钮方式同时也更好发现（见 ADR D19）。
- **多选模式下不响应拖出**。拖出是单条动作，与勾选共用左键，同时支持会让用户分不清
  "按住拖动"是拖走这一条还是拖走整个选中集合。
- **多选保留所有条目**：文件 / 文件夹取 `Path`，无源图片取缓存 PNG 的 `CachePath`，纯文字取原文；
  文本视图按列表顺序生成，文件同时挂载 `CF_HDROP`，因此不同目标应用可以选择自己支持的格式。
- **顺序按列表顺序（钉住项在前），而不是点击先后**。用户看到的顺序就是清单里的顺序，
  贴进 AI 会话后与界面一一对应。
- **同时挂载 `CF_UNICODETEXT` 与 `CF_HDROP`**。AI 会话读取完整文本，资源管理器和微信读取文件列表；
  纯文字选择时仍只写入 `CF_UNICODETEXT`。
- **选中态的视觉只由条目自身的 `IsSelected` 驱动，不判断"当前是不是多选模式"**。条目模板里绑到
  更上层元素（如窗口）的 `RelativeSource` 触发器在容器实现阶段不一定解析得到，表现就是"样式时有时无"。
  普通模式下的选中由 `OnItemClick` 在鼠标抬起时立刻清掉（顺带彻底解决"点击后残留选中底色"），
  多选模式才保留选中，于是同一条 `IsSelected` 触发器在两种模式下都成立。

`PathListFormatter` 放在 Core、不依赖 UI，因此同一段逻辑可直接被 FR-61「整组复制路径清单」复用。

两个实现坑（`scripts/verify-multiselect.ps1` 逐条验收：进入多选、勾选 3 条、计数、
复制清单、状态栏回执、跳过文字、退出多选）：

1. **退出多选必须先清空选中，再切回 `SelectionMode.Single`**。单选模式下 `SelectedItems`
   是只读集合，反序操作会抛 `InvalidOperationException`——界面表现就是"点了『完成』没反应"。
2. **自动化验收必须用真实鼠标点击勾选**。UI Automation 的 `SelectionItemPattern.Select()`
   会顶掉上一条选中，即使列表处于多选模式，也选不出多条。

### 8.6.1 设置窗口（FR-72 / FR-74 / FR-75，2026-10-08 设计，同日改版）

`ShelfSettings` 的 `Capacity` 与 `TimeToLiveHours` 早已落盘且生效（实测 `capacity=3` 有效），缺的只是一个能改的界面。2026-10-08 追加 `ClearOnExit`（FR-74）、`EnableWorkspace`（FR-75），两者同为可选项，同样收进这一个窗口。

**放在哪里**：**独立设置窗口**，托盘只留一条「设置…」入口。

这个决策改过一次：初版决定做成托盘子菜单 + 枚举档位，实测后推翻。理由有三条，前两条是硬伤：

| 问题 | 说明 |
| --- | --- |
| **放不下自定义输入框** | 枚举档位能塞进子菜单，自由输入框塞不进——用户明确要求"上限设置可以自定义加入配置项" |
| **子菜单会越来越深** | 设置项在增长（清理策略 → 退出清空 → 工作区 → 自动收录 → 配色）。第三层以后没人找得到，而托盘菜单本身没有搜索 |
| 独立窗口并非"哪都找不到" | 初版担心"不进任务栏 = 用户找不到设置"。实际不需要进任务栏：托盘图标右键就是入口，双击唤回主面板；设置窗口只是 `ShowInTaskbar=False` 的普通模态，唤出即可见 |

**取值放开为自由输入**（用户明确要求，FR-72）：

| 项 | 控件 | 取值 | 兜底 |
| --- | --- | --- | --- |
| 临时区上限 | 数字输入框（`NumberBox`） | 1～99，默认 9 | `Math.Clamp` 在 `ShelfWindow.SetCapacity` 入口钳制；`ShelfSettings.SafeCapacity` 再兜一层 |
| 条目过期时长 | 数字输入框（`NumberBox`） | 1～720 小时（30 天），默认 24 | `Math.Clamp` + `ShelfSettings.TimeToLive` 的 `Clamp` 双层 |
| 退出时清空 | 开关（`ToggleSwitch`） | 默认**关** | 不可逆动作，不能默认开 |
| 启用工作区 | 开关（`ToggleSwitch`） | 默认**关** | 界面未实现完，默认开等于让用户以为已有分组 |
| 自动收录下载 / 微信目录 | 开关（`ToggleSwitch`） | 默认关 | 红线 R6 |
| 配色 | 两个文字按钮 | Frappe / RosePineDawn | `PaletteService.Normalize` 收敛未知值 |

初版担心"自由输入容易输错"，用枚举档位挡住。现在的判断是：**有钳制 + 有边界提示 + 有回显就不需要枚举**。真正防输错的是这三层，而不是限制可选项的个数——枚举也挡不住 `state.json` 被手改。

**落地要点**：

| 项 | 设计 |
| --- | --- |
| 不自持状态 | 设置窗口**不自己保存任何配置**，所有读写转发 `ShelfWindow.Set*`，由主窗口统一 `ScheduleSave()`。避免两份状态各写一半、关窗时互相覆盖，也让钳制逻辑只存在于一处 |
| 回填不触发保存 | `Loaded` 里程序化赋值会触发 `Checked/Unchecked`。用 `_loading` 标志挡掉，否则用户只是打开窗口就被当成改了配置、白写一次盘 |
| 回填非法输入 | 输入框失焦后**无条件回填**钳制后的值。空、字母、`12abc`、`0` 都要有确定的落地结果，不能留在框里让用户猜 |
| 输入校验 | 只接受纯整数（`NumberStyles.None`，允许前后空白）。`int.TryParse("12abc")` 会得到 12，那是静默吞掉误输入，宁可判为无效 |
| 上下键微调 | 数字框绑定 ↑/↓ 各 ±1、Enter 移焦提交。设置数值最常见的是"差一点"，翻一格比全选重打快 |
| 控件自绘 | WPF 默认 `CheckBox` / `TextBox` 是灰底白框，在深色面板上刺眼。`Theme.xaml` 里加 `ToggleSwitch`（28×16 胶囊轨道 + 10 px 圆钮）与 `NumberBox`（`PART_ContentHost` + 圆角边框），颜色只绑语义令牌（8.2、R9） |
| 立即生效 | 上限同步 `_shelf.Capacity = value`（setter 内部触发 `Trim()`），淘汰条数经 `Status()` 回报——**淘汰不可逆**，必须让用户知道刚才发生了什么 |
| 越界也要回报 | 输入被 `Math.Clamp` 修正时，`Status()` 追加"（已修正为合法区间 1～99）"，不静默改写 |
| 过期时长边界 | **只影响下次启动的清理**，运行中不扫描、不删除任何条目——保持"退出不清理"这条既有约定（见 5.5） |
| 退出清空的执行顺序 | `OnClosed` 里必须**先清后存**。反过来的话会把刚清掉的条目写进 `state.json`，下次启动又原样回来，开关等于没开。只清未钉住的，与手动清空一致（4.4） |
| 风险说明常驻 | 退出清空旁一行 Support 色文字写明"钉住的保留、源文件不受影响"。这是不可逆动作，不该靠试错才知道 |
| 工作区开关 | 开启立即显示标签与分组入口，关闭只隐藏入口，已保存的分组和条目不清理 |
| 配色选中态 | 用**字重**（SemiBold）而非选中底色——底色与卡片同色系，浅色系下几乎看不出差别，字重差别两套配色里都读得出来 |
| 单实例 | `ShelfWindow.ShowSettings` 持有 `_settingsWindow` 引用，反复点托盘只 `Activate()` 已开的那扇，最小化时先恢复 |
| 拖盘关闭 | 托盘的「设置…」旁边保留「收起」，避免设置窗口把浮窗盖住后无从收起 |

### 8.7 图标与插画（两层素材）

界面里不再出现 emoji 与图标字体字形：`📌` 是彩色 emoji，字体、基线、配色都不受控；Segoe MDL2 字形在部分 Windows 版本上会缺字或变形。两层素材的做法与现状：

| 层 | 做法 | 现状 |
| --- | --- | --- |
| 图标 | `Resources/Icons.xaml` 里的 `PathGeometry`：16×16 坐标格、1.5 描边、圆头端点 + 圆角折点。`Stretch="None"` + 显式 16×16 保证线宽恒定不被拉伸，需要 20 px 时用 `Viewbox` 包一层。颜色只绑语义令牌，不写死在几何体里 | 已落地：收纳托盘、文件夹、文件、文字、图片、钉住（描边 / 实心两种）、定位、删除 |
| 插画 | 空状态那张"托盘 + 两张柔焦卡片 + 玫瑰记号" | **暂缓位图版**，当前用矢量，见下 |

空状态插画现阶段直接画在 `ShelfWindow.xaml` 里，同样只用语义令牌取色（玫瑰用主色、后排卡片用辅色、叶子用点缀色），因此换配色时插画跟着变，不需要维护两份图；**只在列表为空时渲染**，不铺满面板。

**为什么暂缓位图版插画**：位图插画（1x / 2x 透明底 PNG，单张 ≤ 60 KB）依赖可靠的透明通道，而这一版的**透明底实验失败**，暂时不作为可交付方案。矢量路线已经满足"任意 DPI 清晰、不占内存、不引入依赖"（R9），不阻塞主流程；位图插画等透明底产出稳定后再补，届时只换素材、不动结构。

### 8.8 滚动条（2026-10-06 提出，2026-10-08 已实现）

条目列表右侧的上下滑条现在是 **WPF 默认 `ScrollBar` 外观**（灰色轨道、两端箭头按钮、宽 17 px），
与面板的配色、圆角、1.5 px 线宽都不是一套语言，实体上很显眼。自绘规范：

| 项 | 取值 |
| --- | --- |
| 轨道 | 不画底色；滑块之外一律透明 |
| 滑块 | 静止宽 4 px、悬停 8 px，圆角 = 宽的一半；颜色 `StrokeBrush`，拖动中 `AccentBrush` |
| 箭头与翻页按钮 | 模板里直接去掉（`RepeatButton` 不渲染） |
| 显隐 | 鼠标进入列表区域才显形（透明度过渡 120 ms），移出后淡出；避免"一条灰杠常驻" |
| 宽度 | 覆盖在卡片右缘之上，滑条出现/消失不改变卡片宽度（否则文字会横向跳动） |
| 落点 | `Resources/Theme.xaml` 里一套**隐式** `ScrollBar` Style（`ShelfWindow.xaml` 的 `ListBox` 自动继承），**颜色只绑语义令牌**，两套配色自动跟随（见 8.2） |

> 不写死颜色、不引第三方控件库：与 8.2「颜色全部来自配色字典」和红线 R9 保持一致。

实现时的三个 WPF 陷阱（都是**静默失效**，不报错，只能靠审查发现）：

| 陷阱 | 后果 | 正确做法 |
| --- | --- | --- |
| `TargetName` 只在**同层 `ControlTemplate`** 内有效 | 把显隐触发器写在 `ScrollBar` 的模板里、用 `TargetName="Bd"` 引用 `Thumb` 模板内的 `Border`——运行时"设了但没反应" | 显隐与滑块状态触发器全部放进 `Thumb.Template` 内 |
| `Opacity=0` 的元素**不参与命中测试** | 淡出整个轨道后既不能拖、也不能悬停唤回，自相矛盾 | 显隐只打滑块（`Bd`），轨道始终透明但可命中——"看不见但能拖"；也不能给 `ScrollBar` 自身设 `Opacity=0` |
| `Thumb.IsMouseOver` 只覆盖滑块本身 | 鼠标停在轨道空白处不显形，成了"滑块附近才显形" | 用 `DataTrigger` + `{Binding IsMouseOver, RelativeSource={RelativeSource AncestorType=ScrollBar}}` 取整条滚动条的悬停态 |

另：带 `x:Key` 的是**显式**资源（用 `StaticResource` 引用），不带的是**隐式**样式（自动作用于所有 `ScrollBar`）。两者若都是隐式且同 `TargetType`，后一条会覆盖前一条，列表滚动条会退化成"永远隐藏"。

### 8.9 搜索栏（FR-44）

搜索栏放在面板操作头与条目列表之间，左侧为搜索输入框，右侧为类型筛选按钮。它随展开面板显示，切换临时区 / 工作区分组时保留当前筛选条件，但列表作用域和多选状态仍按现有规则切换。

搜索输入不使用占位文字模拟状态，避免占位内容被当成真实查询；按钮上的当前类型使用中文文案并在菜单中以勾选标记当前值。搜索与筛选均只刷新 `ICollectionView`，不触碰 `ShelfService.Items`，因此不会触发保存、排序或容量淘汰。
