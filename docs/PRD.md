## 1. 产品定位

**一句话**：一个贴在屏幕右下角的常驻小框，把"从哪拿"和"放哪去"解耦——随手把文件、文件夹、文字、图片放进去，需要的时候再拿出来交给微信、AI 会话或任意目标应用。

**不做什么**：它不是剪贴板历史库（不堆积时间线），不是文件管理器（不管理目录树），也不是云盘中转（不联网）。

## 2. 背景与问题

基于本机实测，问题可复现：

| 问题 | 证据 |
| --- | --- |
| 文件名无语义 | 下载目录里 40+ 个 UUID/哈希命名文件（`4a2f6bd6-…-full.mp4`），以及 2 个 `.temp` 文件 |
| 微信接收文件偶发乱码 | 微信数据目录按月分桶（`xwechat_files\wxid_***\msg\file\2026-09\`），抽样批次文件名正常，说明乱码是特定发送端的编码问题 |
| 来源分散 | 微信接收目录、下载目录、各项目目录三处割裂，跨目录搬运必须来回切窗口 |
| 多段文字搬运成本高 | 需要复制一段、切应用、粘贴、再切回来复制下一段，重复 N 次 |
| 常用文件反复找 | 经常要用的文件躺在深层目录里，每次都得重新翻 |

## 3. 目标用户与使用环境

| 项 | 内容 |
| --- | --- |
| 主要用户 | 单人自用（重度跨应用文件搬运、常用微信与 AI 会话、同时维护多个项目） |
| 操作系统 | Windows 11（向下兼容 Windows 10 1809+） |
| 关键外部应用 | 微信 4.x、Codex 桌面版、资源管理器、浏览器 |
| 典型显示器配置 | 多显示器 + 125%～200% 缩放 |

## 4. 产品目标

### 4.1 目标（可衡量）

1. 完成一次跨应用投递（文件或文字）的操作步骤从 6 步以上降到 2 步以内（放进架子 → 在目标处粘贴）。
2. 全程零拷贝：同一个文件在硬盘上始终只有一份，不产生额外副本。
3. 随手可用：唤出浮窗不超过一次快捷键或一次鼠标移动。

### 4.2 非目标（明确不做）

| 不做 | 原因 |
| --- | --- |
| 微信窗口自动化（自动切窗口/选聊天/发送） | 属注入式 UI 自动化，微信每次更新都可能失效，存在账号风险，投入产出比极差 |
| 云同步 / 跨设备 | 与"本地零拷贝"的核心模型冲突，且涉及隐私与网络 |
| 文件内容编辑 | 不是本产品职责，交给原应用 |
| 全盘文件索引与搜索 | 资源开销大，且"搜索文件"已有系统与第三方方案 |
| 剪贴板全历史记录 | 那是剪贴板管理器的领域，本产品只做"当前任务的暂存台" |

## 6. 功能需求

优先级定义：**P0 = 第一版必须有**；**P1 = 解决原始痛点的增强**；**P2 = 锦上添花**。

### 6.1 常驻与浮窗

| 编号 | 需求 | 优先级 | 验收标准 |
| --- | --- | --- | --- |
| FR-01 | 托盘常驻；浮窗具备收起（胶囊把手）/ 临时区 / 工作区三种状态 | P0 | 三种状态可自由切换，收起态显示条目数量徽标；**贴在屏幕边缘时收起态改为细长竖条**（待确认，见技术框架设计 ADR D26） |
| FR-02 | 三种展开触发：点击（把手 / 托盘 / 全局快捷键）、**拖拽经过热区自动展开**、静止悬浮展开（可选） | P0 | 拖拽文件经过收起态热区时面板立即展开，可直接松手放入；**静止悬浮展开默认关闭**——它与"按住胶囊拖动"抢同一个动作（见 ADR D24），开启时带 300 ms 延迟 |
| FR-03 | 浮窗不抢焦点、不进 Alt+Tab、显示时不打断当前输入 | P0 | 展开/收起时目标应用的输入框光标与输入法状态不变 |
| FR-04 | 全局快捷键唤出/收起；快捷键把当前剪贴板内容收进架子 | P0 | 快捷键可在设置中修改，默认不与其他常用软件冲突 |
| FR-05 | 记住浮窗位置；多显示器与不同缩放比例下正确显示 | P1 | 125% / 150% / 200% 缩放下布局无错位 |
| FR-06 | 收起方式：悬浮展开时鼠标移出 1.2 s、**双击面板空白处**、再按一次快捷键、点收起按钮 | P0 | **悬浮展开**的自动收起（**仅在静止悬浮展开开启时生效**，见 ADR D24）；主动展开（点击/快捷键/拖拽）的面板常驻，只有显式操作才收起；面板失去焦点时不自动收起。**Esc 不可用**：窗口带 WS_EX_NOACTIVATE 永不激活，收不到键盘事件，故以双击空白处替代 |
| FR-07 | 置顶保持：被其他置顶窗口覆盖后自动抢回最上层 | P0 | 被覆盖后 5 秒内自动回到最上层，且全程不抢输入焦点 |
| FR-08 | 找回入口：托盘图标（含显示/收起/清空/退出）与全局快捷键唤出 | P0 | 无论窗口被什么遮挡，都能通过托盘或快捷键唤回 |

| FR-21 | 多选复制所选内容；文件保留 CF_HDROP 与路径文本，文字按列表顺序保留 | P0 | 资源管理器/微信可粘贴文件，AI 会话可获得完整路径与文字内容 |

| FR-71 | 自动采集开关（目录监听、剪贴板监听） | P0 | **默认全部关闭** |

| FR-73 | 开机自启、深浅主题跟随系统 | P1 | 自启可在系统设置中看到对应项 |

## 7. 非功能需求

| 编号 | 需求 | 目标值 |

## 9. 数据与隐私要求

1. 只保存文件路径与少量元数据（显示名、来源、时间），不保存文件内容副本；唯一例外是无源文件的图片（存一张缓存 PNG）。
2. 状态文件保存在 `%LOCALAPPDATA%\`，缓存目录可被安全清空而不影响用户原始文件。
3. 不记录用户输入的文字内容之外的信息；不采集使用统计。
4. 默认关闭自动采集，用户主动放入的内容才进入架子。

## 11. 验收标准（整体 DoD）

一个版本算完成，需要同时满足：

1. P0 需求全部通过对应验收标准，且有对应的手工验收记录。
2. 核心逻辑单元测试通过（命名修复、路径清单、条目存储、过期清理）。
3. 内存、CPU、冷启动达到 NFR-01～03 的目标值。
4. 退出后缓存目录为空，且原始文件零改动（可用文件哈希校验）。
5. 文档同步更新：需求变更必须回写本 PRD 与 [技术框架设计](./技术框架设计.md)。

## 13. 风险与依赖

| 风险 / 依赖 | 影响 | 应对 |
| --- | --- | --- |
| 本机只有 .NET 运行时、无 SDK | 无法开始编码 | 先安装 .NET SDK（约 200 MB，一次性） |
| 微信粘贴/拖放行为未实测 | 影响投递通道设计 | 先完成调研文档 6.4 节的手工实测 |
| 微信接收目录结构随版本变化 | 自动进架失效 | 目录可配置；监听失败不影响手动放入 |
| 长路径与权限问题 | 个别文件无法读取 | 明确提示，不静默失败 |
| 浮窗遮挡或干扰其他软件 | 影响日常使用 | 贴边隐藏 + 可全局快捷键模式运行 |

## 14. 待确认问题

1. 微信 4.x 中粘贴文件（`Ctrl+V`）是否能作为附件发送？若不能，文件场景是否只保留拖拽与"发送到"？
2. 产品名已定：发布名为「花托 · Blossom Rest」，代码代号保留 `TransitShelf`（ADR D22）；商标核验已完成，未查到相同或近似的在先注册。
3. 是否需要"移动到…"（真实移动文件）还是只保留复制粘贴与拖拽？
4. 收起态贴在屏幕边缘时是否改为竖条（ADR D26）？按住竖条拖动是移动窗口位置，还是把面板拉出来？是否需要"完全隐藏、只留快捷键唤出"的模式？
5. 条目列表滚动条的自绘规格（技术框架设计 8.8）：常显还是鼠标悬停显形？
