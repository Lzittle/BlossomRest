## 0. 结论速览

1. **需求成立且真实。** 本机实测已复现你描述的问题：浏览器/工具下载目录里堆积 40+ 个 UUID、哈希命名的文件（如 `4a2f6bd6-2b45-44ed-8491-ce4ec269ea63_full.mp4`），文件名完全无语义；工作区目录里散落着 Agent 生成的产物；微信接收目录按月份分桶（`xwechat_files\wxid_***\msg\file\2026-09\`），跨目录搬运文件必须来回切窗口。
2. **效果可实现，难度中等。** 核心技术就是 Windows 原生的 OLE 拖放（入站 `IDropTarget`、出站 `DoDragDrop`），这是 Windows 上二十年稳定的系统能力。真正的难点不在"拖"，而在"拖出后目标应用是否接收"，以及窗口行为细节（置顶、不抢焦点、多屏、边缘吸附）。
3. **不要用 Electron / 网页壳做。** Electron 官方的出站拖拽 API 只支持文件路径与拖拽图标，**不支持直接拖出纯文本或位图**（详见 3.2 节原文引用）。这意味着"拖一段文字到微信输入框"这类核心场景在 Electron 里做不了，只能落临时文件绕路。
4. **没有可直接安装使用的同类产品。** 直接同类（拖拽暂存架）在 macOS 上有成熟的商业产品线（Yoink / Dropover / Dropzone），在 Windows 上目前**只有 0～9 星的开源雏形**，且多为 2026 年下半年新建；剪贴板管理器（CopyQ、Ditto 等）能力接近但不解决"多段文字 + 图片 + 文件混合暂存"的诉求。
5. **架构定稿为「引用式暂存」（零拷贝）。** 架子里只存指针不存副本，同一个文件在系统里始终只有一份；投递时唯一的一次数据搬运发生在粘贴/落盘那一刻。这也是内存开销最小的做法（详见第 5 章）。
6. **跨应用投递以复制粘贴为主通道，拖拽降级为可选增强。** 粘贴走的是系统通用通道，兼容性最好（微信、浏览器、任何应用都支持 Ctrl+V）；拖拽要好用与否取决于目标应用，作为加分项而非必需项。
7. **微信窗口自动化明确出范围。** 自动切窗口、自动选聊天、自动发送属于对第三方客户端的注入式自动化，脆弱且有账号风险，投入产出比极差，不做。
8. **"放进框里"是用户主动选择，不是自动拦截。** 自动收录（目录监听、剪贴板监听）一律做成可选开关，默认关闭；默认行为是"我自己把文件/文件夹放进去"。

## 1. 需求还原

### 1.1 你说的问题 → 真实诉求

| 原始描述 | 真实诉求 | 工具应提供的能力 |
| --- | --- | --- |
| 微信保存的文件名是乱码 | 拿到文件后想立刻知道"这是什么、要不要留" | 落地即捕获 + 名称修复/重命名 + 预览 |
| 下载在 Download 文件夹，Agent 生成的又散在项目里 | 文件分散在多个位置，找回来成本高 | 多来源汇总（监听目录 / 手动拖入 / 程序投递） |
| 想复制分开的多段文字或图片，每次都要开微信翻聊天记录 | 需要一个跨应用的"剪切板暂存区" | 文本/图片/文件混合暂存，可拖出、可点击复制 |
| 放在屏幕右下角，保留几个，随时清理 | 随手可用的轻量浮层，不占桌面、不丢数据 | 常驻置顶小窗 + 数量上限 + 过期/一键清空 |
| 拖进 AI 会话或微信 | 跨应用投递，且要"拖得过去" | 原生出站拖放（文件/文本/图片三种格式） |

### 1.2 场景清单（用于验收）

| 编号 | 场景 | 成功判定 |
| --- | --- | --- |
| S1 | 从资源管理器拖 3 个文件进中转站，切到微信聊天窗口再拖出 | 微信弹出"发送文件"确认并成功发送，中文名不乱码 |
| S2 | 从中转站拖 1 段文字到微信输入框 | 文字出现在输入框（若微信 4.x 不支持，则退化为"点击复制 + 手动粘贴"） |
| S3 | 拖 1 张图片到 Codex 会话输入框 | 会话里出现图片附件 |
| S4 | 微信收到乱码名文件，5 分钟内自动出现在中转站并可一键改名 | 改名后原文件同步重命名 |
| S5 | 工作到一半关掉工具，重新打开 | 置顶项还在，未置顶项已按策略清理，临时文件无残留 |

### 1.3 v1.1 补充确认的设计取向

| 你的判断 | 采纳结论 | 落在哪一节 |
| --- | --- | --- |
| 拖拽作为可选项 | 采纳。拖入仍进 P0（原生栈下成本很低），拖出降级为 P1 的可选增强 | 5.1、6.2 |
| 复制粘贴作为兜底 | 采纳并升级为**主通道**——粘贴的兼容性优于拖拽，任何应用都支持 | 5.1、5.7 |
| "虚假暂存"：只做最初到最终的一次搬运 | 采纳，定稿为引用式暂存：架子只存指针，文件全程只有一份 | 5.2、5.3 |
| 送到 AI 里用引用地址 | 采纳，并升级为 P0 功能：多选生成绝对路径清单，直接贴进会话 | 5.7、6.2 |
| 点击可追溯到文件夹地址 | 采纳，右键"在文件夹中显示"调用系统定位 | 5.7 |
| 相当于常用文件工作区的置顶 | 采纳，扩展为"临时区 + 常驻工作区"双层结构 | 5.6 |
| 微信跳转难度大、性价比低 | 采纳，明确出范围，只保留"复制后自己粘贴" | 5.5 |

### 2.4 为什么不能直接装一个用

1. **剪贴板管理器解决的是"历史"，你要的是"当前任务的工作台"。** 历史库会一直堆积，反而需要清理；你要的是默认只留 3～9 个、随时清空、拖完即走。
2. **"乱码修复"和"多来源汇总"没人做。** 调研到的全部项目都不涉及微信接收目录监听、文件名乱码还原、下载目录汇总。
3. **Windows 侧的同类开源项目全都没有社区验证。** 直接同类的最高星数是 DropPoint（1,093★，Electron，跨平台但拖出能力受限），Windows 原生实现全部在 0～9 星，等于没有可依赖的产品。

**结论：自研。** 但可以把 Bucket（C#）和 DropPoint 当行为参考，把 OpenYoink 的"拖成功才离架"、TieZ 的"贴边隐藏"作为交互基准。

## 3. 技术可行性评估

### 3.1 拖入（把东西放进中转站）—— 低风险

- 文件：注册窗口为拖放目标（原生栈为 `IDropTarget` / `WM_DROPFILES`），即可接收 `CF_HDROP`（文件路径列表），支持多选、文件夹。
- 文字：接收 `CF_UNICODETEXT`（以及来自 Word/浏览器的 `CF_HTML`）。
- 图片：接收 `CF_DIB` / `CF_DIBV5` / `PNG` / 文件路径形式。
- 另外一个入口是**剪贴板监听**：用户按 Ctrl+C 后主动"收录到中转站"（比全自动更安全，见 5.4 与 R8）。

### 3.2 拖出（从中转站投递到微信/AI 会话）—— 核心风险点，但可控

Windows 出站拖放通过 `DoDragDrop` 一次携带多个剪贴板格式，实现"目标要什么就给什么"：

| 载体 | 必须提供的格式 | 说明 |
| --- | --- | --- |
| 文件 | `CF_HDROP`（文件路径列表） | 微信聊天窗口、资源管理器、浏览器上传区都认这个，支持一次多个 |
| 文字 | `CF_UNICODETEXT`（+ 可选 `CF_HTML`） | 粘贴板、Word、浏览器输入框认；原生控件类接收端认 |
| 图片 | `CF_DIB` + `PNG` | DIB 兼容性好，PNG 对浏览器/Chromium 类目标友好；两者都挂上，让目标自选 |

**关键限制（已核实）**：Electron 官方的出站拖拽接口只有文件路径，没有文本/位图：

> `contents.startDrag(item)` — `item.file` string（被拖拽文件的路径）、`item.files` string[]（可选，会覆盖 `file`）、`item.icon`（拖拽时跟随鼠标的图标）
> 出处：Electron 官方文档 `docs/api/web-contents.md`

这带来三个直接后果：

1. 用 Electron/Tauri 网页壳做不出"拖一段文字到微信输入框"，只能先写成临时 `.txt` 再拖文件——而微信收到的是"文件"而不是"输入框里的一段文字"，与你的诉求不符。
2. 拖图片也需要先落临时文件，会产生残留文件与清理负担。
3. 常驻一个 Chromium 运行时来显示一个 200×200 的小窗，内存与体积代价不成比例（DropPoint+ 的作者在 README 里也正是因为这个放弃 Web 层）。

**结论：出站拖放必须走原生实现，一次携带文件/文字/图片三种格式。**

### 3.3 技术栈对比

| 技术栈 | 拖入 | 拖出文件 | 拖出文字 | 拖出图片 | 体积/内存 | 开发效率 | 结论 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| **C# + WPF（.NET）** | ✅ | ✅ | ✅ | ✅ | 小（几十 MB，常驻 <80 MB） | 高，本机已装 .NET SDK | **推荐** |
| C# + WinUI 3 / .NET（Bucket 的做法） | ✅ | ✅ | ✅ | ✅ | 小 | 中，置顶/无激活仍需 Win32 互操作 | 可选 |
| C++ + Qt6（CopyQ 的做法） | ✅ | ✅ | ✅ | ✅ | 小 | 低（开发慢） | 备选 |
| Python + PySide6/Qt6（DropPoint+ 的做法） | ✅ | ✅ | ✅ | ✅ | 中（常驻 80～150 MB，打包 60～150 MB） | 高 | 备选，见 7.8 |
| Java 21 + JavaFX | ✅ | ✅ | ✅ | ✅ | 大（JVM 常驻 150～300 MB，打包 150 MB+） | 低 | 不推荐，见 7.8 |
| Rust + Win32 API | ✅ | ✅ | ✅ | ✅ | 极小 | 低（需手写 OLE 层，生态参考少） | 备选 |
| Electron | ✅ | ✅（仅路径） | ❌ 需落临时文件 | ❌ 需落临时文件 | 大（150 MB+） | 高 | **不推荐** |
| Tauri（TieZ/PasteBar 的栈） | ✅ | 需自写 Rust 侧代码 | 需自写 Rust 侧代码 | 需自写 Rust 侧代码 | 中 | 中 | 不推荐（改造量≈重写） |
| AutoHotkey | ⚠️ 仅文件 | ❌ | ❌ | ❌ | 极小 | 高 | 排除 |

> 注：Python 与 Java 的拖放能力本身是完备的（PySide6 的 `QDrag`+`QMimeData`、JavaFX 的 `Dragboard.putFiles/putString/putImage` 都支持三种出站格式），它们被排除的理由不是"做不到"，而是系统集成成本与资源占用，详见 7.8。

### 3.4 目标接收端兼容性

| 接收端 | 本机情况（实测） | 拖文件 | 拖文字 | 拖图片 | 备注 |
| --- | --- | --- | --- | --- | --- |
| 微信（新版 Weixin 4.x） | 程序位于 `C:\Program Files\Tencent\Weixin\Weixin.exe`，数据位于 `C:\Users\<user>\xwechat_files` | 预期 ✅ | **待实测** | **待实测** | 4.x 客户端是新架构，输入框是否为 OLE 文本目标需实测；图片优先给 PNG |

### 3.5 本机环境约束

- 已具备：Node.js 24、.NET SDK 7、Python。**不需要**额外安装即可用 C# 起步。
- 多显示器 / 高 DPI / 任务栏位置变化：需要处理 `WM_DPICHANGED` 与显示器工作区变化，否则窗口会漂移。
- 独占全屏（游戏、部分播放器）下置顶窗口不会显示，属系统行为，需提供"全屏时自动隐藏"开关。

## 4. 风险清单与优化建议

以下按"问题 → 影响 → 建议"给出，标 P0 的必须进第一版。

| 编号 | 问题 | 影响 | 建议 | 优先级 |
| --- | --- | --- | --- | --- |
| R1 | 出站拖放的完整性级别限制（UIPI）：低权限进程不能把数据投给高权限窗口，反之亦然 | 中转站若以管理员身份运行，从资源管理器往里拖会失败；普通权限运行时，拖给管理员窗口也会失败 | **中转站必须以普通用户权限运行**，并在检测到提升运行时给出提示 | P0 |

## 5. 引用式暂存架构（v1.1 定稿）

### 5.1 三条设计原则

| 原则 | 含义 | 为什么 |
| --- | --- | --- |
| **引用优先（零拷贝）** | 架子里保存的是"指针"，不是内容副本 | 文件在硬盘上始终只有一份，不产生重复文件、不占额外空间、不出现"改了原件但架子里是旧版"的分裂 |
| **粘贴为主、拖拽为辅** | 跨应用投递的默认动作是"点击条目复制 → 目标处 Ctrl+V"；拖拽作为可选增强 | 粘贴走系统通用通道，任何应用都支持；拖拽受目标应用实现质量影响，容易在个别软件上失效 |
| **可追溯** | 每个条目都能一键回到它在硬盘上的位置 | 你提的"点击追溯到文件夹地址"，也是"虚假暂存"能成立的前提 |

### 5.2 条目数据模型

| 条目类型 | 架子里存什么 | 单条开销 | 源文件消失时 |
| --- | --- | --- | --- |
| 文件 | 绝对路径 + 显示名 + 来源目录 + 收录时间 | ≈ 200 字节 | 条目标记为"已失效"，不自动删除（防止误操作） |
| 文件夹 | 同上 | ≈ 200 字节 | 同上 |
| 文字 | 文字内容本身（UTF-8） | 几 KB | 无此问题 |
| 图片（有源文件） | 路径 | ≈ 200 字节 | 标记"已失效" |
| 图片（无源文件，如截图工具或网页直接复制的位图） | 落到缓存目录的一张临时 PNG | 磁盘 0.3～3 MB | 由工具自己管理，随过期策略清理 |

**唯一需要落盘的特殊情况是无源文件的图片。** 因为剪贴板里的位图一旦被别的复制操作覆盖就彻底没了，必须在中转站自己的缓存目录留一份 PNG 才能"扛得住"。这条设计同时也为拖出提供了文件载体（见 3.2）。

### 5.3 回答"每次复制粘贴是不是很占内存"

先给结论：**文字和文件几乎不占内存，唯一要留意的是图片；而只要坚持引用式暂存 + 缩略图按显示尺寸加载，内存开销基本可以忽略。**

| 载体 | 真实开销 | 说明 |
| --- | --- | --- |
| 文字 | 几 KB | 可以完全忽略 |
| 文件（复制到剪贴板） | 几百字节 | 剪贴板里放的是路径列表（`CF_HDROP`），**并不搬运文件内容**；真正读字节只发生在粘贴落地那一刻，且由系统完成 |
| 文件（架子里保留） | ≈ 200 字节/条 | 只是路径字符串 |
| 图片（剪贴板位图形式常驻） | 宽 × 高 × 4 字节：1080p ≈ 8 MB，1440p ≈ 15 MB，4K ≈ 33 MB（通常还会再附带一份 PNG 压缩副本） | 这才是真正吃内存的形态。若把 5 张截图一直以位图形式留在内存里，会持续占用 40～80 MB |
| 图片（存为临时 PNG） | 磁盘 0.3～3 MB/张 | 内存里只保留按显示尺寸缩放的缩略图 |
| 缩略图 | 显示尺寸 × 4 字节，通常几十 KB/条 | 需要懒加载：滚出视野即释放 |

**所以"少一次复制"并不会省下什么；真正会失控的是"用一个常驻影子把大量内容长期留在内存/剪贴板里"。** 你的"虚假暂存"思路恰好避开了这个坑。

### 5.4 剪贴板的真实限制：它不能当"存储"

这一节解释了为什么"把暂存内容放在剪贴板上"这条路走不通，只能用引用式方案：

1. **剪贴板全局只有一格，最后写的人赢。** 你在任何应用里随手 Ctrl+C，架子里的内容就被冲掉了。剪贴板是"传送带"，不是"货架"。
2. **延迟渲染（delayed rendering）：** 很多应用复制时并不立刻把数据写进剪贴板，而是等你粘贴时再向源应用索要。如果源应用已经关闭，就可能粘贴出空白。因此中转站必须自己持有路径（或自己落一份文件），才能真正可靠。
3. **自我干扰：** 工具自己写剪贴板时会被自己的监听再次捕获，需要打"自产标记"（见 R7）。

### 5.5 明确出范围：不做微信窗口自动化

你的判断是对的，这条路难度和风险都不值得：

- 自动切换到指定微信窗口、自动定位到具体聊天、自动发送，属于对第三方客户端的**注入式 UI 自动化**，需要窗口句柄/控件层面的操作，微信每次版本更新都可能失效，还存在账号风险与合规问题。
- **本方案明确不做**。微信侧只保留两种稳定做法：
  1. 点击条目复制 → 在微信里 Ctrl+V（文本、图片通用）；
  2. 文件场景：从架子里拖进微信聊天窗口（可选增强），或在资源管理器里用右键"发送到"。
- 如果确实还想要"把微信切到前台"这一步，最多做一个只调用窗口置前、不注入不自动化的按钮，放在 P2 的可选清单里。

### 5.6 双层结构：临时区 + 常驻工作区

你这次的描述实际上把工具从"临时中转站"升级成了"常用文件工作区的置顶"。建议直接做成两层，两者的清理策略互不干扰：

| 层 | 定位 | 内容来源 | 生命周期 |
| --- | --- | --- | --- |
| **临时区**（默认层） | 随手暂存，用完即走 | 拖入、快捷收录剪贴板、目录监听自动进架 | 上限 9 条 + 24 小时过期；退出时清理未钉住项 |
| **工作区**（置顶层） | 常用文件/资料的置顶工作台 | 手动"钉"进去，可分组（项目 A / 论文 / 微信素材…） | 长期保留，不限条数，可保存为命名列表，一键把整组路径贴进 AI 会话 |

这样"保留几个、随时清理"和"长期常用"就不再互相打架了。

### 5.7 点击语义建议

| 操作 | 行为 | 说明 |
| --- | --- | --- |
| 单击 | 复制 | 文字 → 文本；图片 → 位图 + PNG；文件 → 路径列表，可直接粘到资源管理器或微信 |
| 双击 | 打开 | 文件用默认程序打开，文件夹直接进入 |
| 右键 → 在文件夹中显示 | 定位 | 调用 `explorer /select` 直接高亮该文件，满足"追溯到文件夹地址" |
| 多选 → 复制路径清单 | 生成文本 | 输出换行分隔的绝对路径，直接粘进 AI 会话当引用地址，Agent 可直接读取文件 |
| 按住条目拖动 | 拖出 | 可选增强，同时挂载文件/文本/图片三种格式 |

## 7. 界面规格与技术栈定稿

### 7.1 小框不是"网页"，而是三层状态的原生面板

先纠正一个容易混淆的点：**它不需要做成"页面"**，也不涉及路由、多页跳转、浏览器渲染。它本质上是一个常驻的原生小窗口，只是有几种显示状态。真正的界面工作量在于"贴边隐藏 + 不抢焦点 + 状态切换"这些窗口行为，而不是页面开发。

| 状态 | 尺寸（参考） | 何时出现 | 关键要求 |
| --- | --- | --- | --- |
| 收起态 | 约 140 × 36 的胶囊把手 | 默认，贴屏幕右侧或右下角 | 不抢焦点；显示条目数量徽标；鼠标移入即展开 |
| 展开态（临时区） | 约 280 × 380 | 鼠标移入、点击把手、全局快捷键 | 列出临时条目；支持拖入、多选、滚动 |
| 工作区态 | 约 320 × 520 | 切到"工作区"标签 | 分组展示长期保留的文件，可命名、排序 |

### 7.2 布局结构（三区）

```
┌─ 展开态（默认 280 × 380） ─────────────────┐
│ [临时区] 工作区      搜索…      ⚙   ✕      │ ← 顶部工具条
├────────────────────────────────────────────┤
│ 📁 示例文档6.0.pptx               3 分钟前 │
│    ▸ 复制   ▸ 打开   ▸ 定位                 │ ← 条目卡片（悬停显示操作）
│ 📄 示例方案_项目计划书.docx        12 分钟前 │
│ 🖼 截图 20260101-1200          📌 钉住      │
│                                            │
├────────────────────────────────────────────┤
│ 7 / 9 条 · 最早 22:40 过期        [清空]    │ ← 底部状态条
└────────────────────────────────────────────┘
```

1. **顶部工具条**：临时区 / 工作区切换、搜索、设置、折叠。
2. **中部条目区**：卡片列表（可按需切换成网格缩略图）。每张卡片 = 类型图标或缩略图 + 显示名 + 相对时间 + 悬停操作按钮。
3. **底部状态条**：条目数 / 上限、最近一条的过期时间、清空入口、（可选）"移动到…"入口。

### 7.3 交互定义

| 操作 | 默认行为 | 说明 |
| --- | --- | --- |
| 单击卡片 | **按类型**：文件夹 → 打开；文件 / 文字 / 图片 → 复制 | 文件夹没有"复制内容"语义；文字与图片的自然动作是搬运（详见 7.3.1） |
| 双击卡片 | **打开** | 文件夹进入目录；文件用默认程序打开；文字/图片用默认查看器 |
| 卡片上的"定位" | 在父目录中高亮显示该文件 | 满足"追溯到文件夹地址" |
| 展开触发 | 点击把手/快捷键、**拖拽经过热区自动展开**、静止悬浮（300 ms 延迟） | 拖拽时无法点击按钮，热区自动展开是最关键的一条；详见 7.6 |
| 收起触发 | 鼠标移出 400 ms、Esc、再按快捷键、收起按钮 | **失焦不收起**，避免切窗口时面板莫名消失 |
| 拖入卡片区 | 把文件/文件夹/文字/图片放进架子 | 可选能力，但有它体验更顺 |
| 按住卡片拖出 | 投递到目标窗口 | 可选增强（P1） |
| 右键 | 复制 / 复制路径 / 在文件夹中显示 / 钉到工作区 / 重命名 / 移动到… / 删除 | 删除条目绝不删除原始文件 |
| 多选 + 复制路径清单 | 生成换行分隔的绝对路径 | 直接贴进 AI 会话当引用地址 |

**关于"点击打开使用、或者移动传输"**：打开使用 = 文件夹单击、文件双击；传输 = 复制粘贴（主通道）或拖动。其中"移动到…"（选一个目标文件夹，带撤销）建议放进 P1，日常更常用的仍然是"复制 → 到目标处粘贴"。

想按个人习惯调整的话，可给"单击行为"加一个设置项：默认"按类型"（文件夹打开、其余复制），也可整体切换成"统一打开"或"统一复制"。

#### 7.3.1 为什么文件和文件夹的单击动作不同

文件夹单击即打开，因为它没有"复制内容"的自然语义——复制文件夹等于复制路径，价值很低，而"进去拿东西"是它唯一的高频动作。

文件保持单击复制、双击打开，理由是**风险不对称**：误触发"打开"会启动程序或弹出资源管理器并抢走当前输入焦点；误触发"复制"是静默的、无害的、再复制一次就被覆盖了。对一个悬浮在别人窗口之上的工具，前者代价明显更大。

三种类型的默认动作都可以通过设置项整体切换，卡片上也会常驻 `[打开] [复制] [定位]` 三个显式按钮，不依赖用户猜测。

### 7.4 必须设计的界面状态

界面设计不只是画正常状态，下面这些状态不处理就会被当成 bug：

| 状态 | 表现 |
| --- | --- |
| 空状态 | 一句引导："把文件拖进来，或按 Ctrl+Alt+X 收起剪贴板内容" |
| 拖入悬停 | 整框高亮描边，提示"松手即放入" |
| 源文件失效 | 条目置灰 + "已失效"，仍保留入口让用户手动重定位 |
| 过期倒计时 | 底部条显示最近一条的剩余时间；置顶项不参与 |
| 多选 | 选中态描边 + 顶部出现批量操作条 |
| 深/浅主题 | 跟随系统，浮窗半透明毛玻璃，避免遮挡阅读 |
| 高 DPI / 多屏 | 按显示器 DPI 缩放，窗口跟随所在显示器的右下角 |

### 7.5 前端技术栈定稿

这类小面板的"前端"有两层含义，需要分开回答。

**第一层：界面描述层用什么写。** 推荐 **C# + WPF（XAML）**：

| 方案 | 界面描述方式 | 对本场景的适配 |
| --- | --- | --- |
| **C# + WPF（推荐）** | XAML（声明式，支持数据绑定、样式模板、动画） | 做这种列表+小面板绰绰有余；原生控件天然支持拖入拖出；置顶、不抢焦点、贴边隐藏都直接调 Win32；常驻内存小 |
| C# + WinUI 3 | XAML（Fluent 风格更现代） | 外观更好看，但窗口置顶/无激活/贴边隐藏仍要写 Win32 互操作，坑更多，收益不明显 |
| C++ + Qt6 | QML 或 Widgets | 同样胜任，开发效率更低（CopyQ 走的就是这条路） |
| Rust + Win32/GTK | 手写或 GTK | 体积最小，但界面开发成本高 |

**第二层：要不要引入 Web 前端框架（Vue/React）。** **不需要，也不建议。** 理由在 3.2 节已经验证过：套 Web 壳（Electron/Tauri）后，出站拖拽能力被削到只剩文件路径，文字和图片拖不出去；同时为一个 280×380 的小面板常驻一个 Chromium 运行时的内存和体积代价不成比例。让 Web 前端框架来管一个"列表 + 几个按钮"的面板，收益远小于损失。

**折中方案（如果你确实想要 Web 的开发体验）**：只在**设置页/工作区管理页**这类不需要拖放能力的地方用 WebView2 承载，主面板仍用 XAML。这样既保留了 Web 的排版便利，又不牺牲核心拖放能力。

### 7.6 可选性设计（哪些地方给用户开关）

| 层级 | 可选项 | 默认 |
| --- | --- | --- |
| 功能整体 | 是否启用右下角浮窗；是否开机自启；是否启用托盘图标 | 启用浮窗，不自动启动 |
| 收起方式 | 贴边自动隐藏 / 常显胶囊把手 / 仅快捷键唤出 | 贴边自动隐藏 |
| 展开触发 | 点击 / 拖拽经过热区自动展开 / 静止悬浮展开 | 点击与拖拽热区开启；悬浮展开开启但带 300 ms 延迟 |
| 单击行为 | 按类型（文件夹打开、其余复制）/ 统一打开 / 统一复制 | 按类型 |
| 条目来源 | 目录监听（下载目录、微信接收目录）；剪贴板监听 | **都默认关闭**，手动放入 |
| 条目行为 | 单击行为（复制/打开/定位）；是否允许拖出；是否允许自动过期 | 复制 / 允许 / 允许 |
| 清理策略 | 上限条数、过期时长、退出时是否清空、删除是否二次确认 | 9 条 / 24 小时 / 保留钉住项 / 二次确认 |

核心原则：**默认只做"你放进去的东西"，不主动拦截、不自动搜集**；自动化的部分全部交给用户显式打开。

### 7.7 美观性能保证到什么程度

先给结论：**能保证，但保证的方法不是"选一个自带美颜的框架"，而是先把视觉规格定死，再选一个能 100% 实现它的技术栈。**

技术侧的天花板（以推荐栈 C# + WPF 为例）：

| 能力 | 结论 |
| --- | --- |
| 矢量渲染与缩放 | WPF 全程矢量渲染 + 硬件加速，任意 DPI 下不糊 |
| 圆角、阴影、悬停动效 | 原生支持，动画走 GPU 合成，小面板跑满 60 fps 没有压力 |
| 毛玻璃 / 亚克力 | Windows 11 可调用 DWM 的 Mica / Acrylic；WPF 支持无边框 + 透明窗口 + 自绘，能做出半透明磨砂观感（注意不要整窗实时模糊，会掉帧） |
| 默认观感 | **这是唯一的坑**：WPF 自带控件仍是 2008 年的 Aero 风格，直接拖控件出来会显旧。必须套 Fluent 风格控件库（WPF-UI、HandyControl 等）或自绘控件模板 |
| 中文排版 | 系统字体（微软雅黑 / 苹方）+ 明确的字号字重阶梯，不会出现"字挤在一起" |

设计侧则需先确定这份**视觉规格**（定稿后实现照抄，不靠感觉）：

| 令牌 | 建议值 |
| --- | --- |
| 间距阶梯 | 4 / 8 / 12 / 16 px，全局只用这四档 |
| 圆角 | 条目卡片 8 px，面板 12 px，收起胶囊 18 px（全圆角） |
| 字号阶梯 | 11 / 12 / 13 / 15 px，字重 400 / 500 / 600 三档 |
| 颜色 | 语义令牌而非具体色值：背景 / 表面 / 描边 / 主色 / 危险色 / 三级文字，深浅两套主题各一份 |
| 阴影 | 三级；浮窗用 0 8 24 rgba(0,0,0,.18) |
| 动效 | 展开 160 ms ease-out，条目增减 120 ms，悬停 80 ms；禁止回弹、缩放等夸张效果 |
| 密度 | 默认紧凑（单条 44 px 高），可在设置里切换舒适模式 |

**一句话**：美观不是技术栈自动带来的，而是"视觉规格 + 自绘模板"带来的；技术栈只决定这份规格能否被完整实现。上表这套规格在 C# + WPF 上可以 1:1 落地无折扣。

### 7.8 技术选型对比：为什么不是 Python、为什么不是 Java

先说清楚事实：本机 **Python 3.13.14 与 JDK 21 LTS 都已安装**，两者在技术上都能实现"拖入 + 三种格式拖出"。所以排除它们不是因为"做不到"，而是因为这个工具的权重排序是：

> **系统集成能力 > 常驻资源占用 > 打包分发体验 > 开发速度**

而 Python 与 Java 恰好在前三项吃亏，只在最后一项占优。

| 维度 | C# + WPF（推荐） | Python + PySide6/Qt6 | Java 21 + JavaFX |
| --- | --- | --- | --- |
| 置顶 / 不抢焦点 / 贴边隐藏 / 不进 Alt+Tab | 直接调 Win32，几行 P/Invoke，资料充足 | 要靠 `ctypes` 手写 Win32，Qt 只封装了一部分 | JavaFX 没有"不抢焦点窗口"的 API，需 JNA/JNI 打补丁 |
| 系统托盘 | 原生 | 可用，但行为细节少 | AWT `SystemTray` 能力有限 |
| 高 DPI / 多屏 | 原生支持 Per-Monitor V2 | Qt6 尚可 | 需自行处理 |
| 常驻内存 | 通常 < 80 MB | 空窗口即 80～150 MB | JVM 常驻 150～300 MB |
| 打包体积 / 冷启动 | 小 / 快 | 60～150 MB / 1～3 秒 | 150 MB+（需带 JRE）/ 慢 |
| 杀软误报 | 低 | **高**（PyInstaller 单文件是误报重灾区，而本工具要常驻 + 开机自启） | 低 |
| 界面自由度 | 高（XAML + Fluent 控件库） | 高（QSS） | 中（JavaFX CSS） |
| 生态活跃度 | 高 | 高 | 低（桌面 JavaFX 已边缘化，遇到问题难找答案） |
| 与 AI 协作改代码 | 好 | **最好**（语法直白，AI 改写成功率高） | 一般 |

**关于 Python 的诚实评价**：它是唯一一个"合理备选"。如果你更看重"我以后自己能看懂、能让 AI 直接改"，Python + PySide6 完全可行（DropPoint+ 就是这条路）。代价是体积、启动速度、常驻内存和杀软误报——而这三项恰恰是这个"常驻置顶小工具"最敏感的指标。**结论：默认选 C#，若你明确希望代码更易读易改，可以换 Python，我会把规格写成两套等价的实现清单。**

**关于 Java 的诚实评价**：JavaFX 的拖放能力完备，本机也有 JDK 21，但它在这个场景里没有一项占优——系统集成最费劲、资源占用最大、分发最重、生态最冷。除非你已有 Java 代码需要复用，否则不选。

**需要额外说明的一点**：本机 .NET 目前**只装了运行时（7.0.20），没有 SDK**，真正动手前要先装 .NET SDK（约 200 MB，一次性的）。已修正附录 B。
